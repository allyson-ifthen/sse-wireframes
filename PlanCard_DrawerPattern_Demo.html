Plan Card — Drawer Pattern: Design Exploration

This file explores the full-width drawer pattern as an alternative to the current inline accordion for "View Plan Terms & Disclosures." Section 1 shows the problem with inline accordion in a grid. Section 2 shows the drawer pattern — click any card's expand link to see it live. Section 3 covers trade-offs and open decisions.

This is a design exploration, not an approved change. Decisions would be logged in Wireframe_ChangeLog_Active.md before any propagation to PlanCard_Wireframe.html.

✕CTA pushed out of viewport. On a ~768px viewport with the accordion open, "Start Enrollment →" may require scrolling past ~180 words of legal content before it's visible. High friction for a primary conversion action.
✕Grid row height inconsistency. CSS Grid rows align to the tallest cell. An open card stretches the row, leaving whitespace gutters in adjacent closed cards. Visually breaks the grid on desktop.
⚑Multi-row grids compound the problem. If plans wrap to 2 rows (4–6 plans), opening a card in row 1 doesn't affect row 2, but the visual disruption is still jarring for a single row.
2 Drawer pattern — full-width panel below the row Live interaction · click "View Plan Terms" on any card
Proposed pattern — interactive

Click "View Plan Terms & Disclosures" on any card. The drawer opens below the grid row — the card grid layout does not shift. CTA remains visible above the expand link. Click a different card to switch. Click the same card again or "Close" to dismiss.

✓Grid stays stable. Cards never change height. Adjacent cards are unaffected. No whitespace gaps.
✓CTA above expand link. "Start Enrollment →" is always visible between the bullets and the terms link — open or closed.
✓One drawer, shared. Only one plan's terms are visible at a time. Switching cards replaces drawer content — cleaner than two open accordions competing for attention.
↳Dev note. Drawer is appended once to the DOM below the grid container, not inside any card. No grid-row height logic required. Content swapped via JS on each open. Accessible: focus moves to drawer on open, returns to trigger on close.
3 Trade-offs & open decisions Before logging as approved change
Consideration Inline accordion Drawer pattern Verdict
Grid stability Breaks — row expands, whitespace in adjacent cards Stable — cards never change height Drawer wins
CTA visibility CTA pushed below ~180 words of content; may require scroll CTA always visible above the expand link — open or closed Drawer wins
Mobile behavior Natural single-column stack — accordion is idiomatic on mobile Drawer becomes full-width panel below the card (single-col = same visual result as accordion). Needs responsive breakpoint decision. Conditional — use drawer ≥ md breakpoint; revert to inline accordion on mobile
Dev complexity Simple CSS show/hide within card Requires JS to append drawer below grid, swap content, manage focus. Modest — single shared drawer element, not per-card. Slight drawer overhead — confirm acceptable with dev
Accessibility Standard aria-expanded toggle; well-understood pattern Requires focus management (move to drawer on open, return on close) + aria-controls. Manageable but more surface area. Confirm with dev — not a blocker
Analytics plan_details_section_view (already logged in PC-D7) Same event shape — drawer_open replaces expand_open; section_name param unchanged No change to analytics spec
2-plan grid (edge case) Problem remains — one card expands, adjacent has whitespace Drawer still spans full grid width regardless of card count Drawer wins
⚑Open decision: mobile breakpoint. At what viewport width does the drawer revert to inline accordion? Recommend ≤ 767px (single-column layout) — but confirm with dev.
⚑Open decision: drawer width on odd plan counts. 1-plan grid or 2-plan grid — drawer still spans 100% of .plan-grid-wrap. Does the drawer feel oversized on a 1-plan layout? Low-priority edge case.
↳CMS impact. Drawer content (the 4 sections) is still CMS-authored per plan_type — no authoring change required. Rendering location changes, not content model.
